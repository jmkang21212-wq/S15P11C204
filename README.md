# LAIVE

**1인 방송인을 위한 실시간 방송 보조 AI 콘솔**

방송 중에는 채팅 여론·반복 질문·위험 발언을 실시간으로 알려 주고, 방송 후에는 세션 리포트·자동 클립·성장 리포트로 복기를 돕습니다.

- 삼성 청년 SW·AI 아카데미(SSAFY) 15기 2학기 공통 프로젝트 (2026.07 ~ 2026.08, 6인)
- **SSAFY 공통 프로젝트 우수상**

![방송 콘솔](exec/images/console-full.png)

## 주요 기능

### 방송 중

| 기능 | 설명 |
|---|---|
| **채팅 여론·호응도** | 채팅을 8가지 감정으로 분류하고, 최근 구간의 여론 분포와 호응도(유니크 채터 ÷ 시청자)를 1초 단위로 갱신 |
| **LLM 여론 요약** | 3분 주기 자동 요약 + 수동 요약 버튼 |
| **반복 질문 Top N** | 비슷한 질문을 묶어 많이 나온 순으로 보여 주고, 이미 답한 질문은 숨김 |
| **위험 발언 감지** | 스트리머 발화를 실시간 전사해 비속어 사전 매칭과 LLM 문맥 판정으로 경고 |
| **약속 감지** | 방송 중 한 약속(다음 방송 일정 등)을 카드로 잡아 일정에 등록 |
| **미니 모드** | 방송 화면 위에 띄우는 오버레이 창 |

### 방송 후

| 기능 | 설명 |
|---|---|
| **세션 리포트** | 타임라인 복기, AI 요약·개선 제안 |
| **자동 클립** | 하이라이트 구간을 클립으로 생성 |
| **성장 리포트** | 방송 지표 추이와 목표 로드맵 |
| **포트폴리오** | 방송 실적·하이라이트를 모아 비즈니스 매칭에 활용 |

## 시스템 구성

```
치지직 / YouTube ──▶ chat-collector ──▶ Spring Boot ──1초 배치──▶ chat-ai (감정·지표·요약·질문)
                       (채팅·시청자 수집)     │     ◀────── 응답 ──────┘
                                              ├──▶ PostgreSQL(TimescaleDB) / Redis 저장
스트리머 마이크 ──▶ 위험 발언 AI 서버 ─경고─▶ │──▶ Electron 클라이언트 (SSE · WebSocket)
```

- **수집과 분석의 분리**: 채팅 수집·저장·하이라이트 판정은 Spring이 맡고, chat-ai는 Spring이 보낸 배치만 분석합니다. chat-ai가 멈춰도 수집과 저장은 계속되고, 감정 라벨만 비어 있게 됩니다.
- **멀티 플랫폼**: 하나의 방송 세션 아래에 플랫폼별 하위 세션을 두어 치지직과 YouTube를 함께 수집합니다 ([MULTI_PLATFORM_ARCHITECTURE.md](MULTI_PLATFORM_ARCHITECTURE.md)).

## 담당: 채팅 AI 서버 (`AI/chat-ai`)

6인 팀에서 채팅 AI 파이프라인을 맡았습니다. 서비스 백엔드(Spring)는 다른 팀원이 담당했습니다.

| 구현 | 내용 |
|---|---|
| **감정 분류 모델** | KcELECTRA를 한국어 방송 채팅 8감정으로 파인튜닝하고 ONNX로 변환해 CPU에서 추론 |
| **확률 합산 여론 분포** | `/aggregate`는 개별 라벨을 argmax로 세지 않고 채팅마다 확률을 그대로 합산합니다. "웃음 0.45 / 중립 0.40"처럼 애매한 채팅이 한쪽 1표로 몰리지 않습니다 |
| **실시간 지표** | Spring이 1초마다 보내는 배치(`/broadcasts/{id}/ingest`)에 건별 감정과 슬라이딩 윈도우 지표를 함께 응답. 윈도우는 Redis에 두어 서버를 재시작해도 이어짐 |
| **LLM 여론 요약 · 반복 질문** | 3분 윈도우 요약, 임베딩 클러스터링으로 반복 질문 묶기 |
| **리플레이 시뮬레이터** | 과거 방송 채팅을 원래 타이밍대로 재생하는 가짜 치지직 서버. 접속 주소만 바꾸면 운영 코드 그대로 백엔드를 개발·백테스트 |
| **전처리 정본 + 회귀 테스트** | 학습과 서빙의 전처리가 달라지면 에러 없이 성능만 떨어지므로, 전처리를 한 파일로 고정하고 회귀 테스트를 둠 |

### 모델 성능 (골드셋 1,000건)

| 항목 | 값 |
|---|---|
| accuracy / macro-F1 (fp32) | **0.780 / 0.714** |
| int8 양자화 | 약 2배 빠름, macro-F1 1.9점 하락 |
| 알려진 한계 | `분노/불만` 재현율 0.508. 표면 표지(ㅋㅋ, ㅠㅠ, ?)가 없어 의미를 이해해야 하는 라벨이라, 부정 여론 알림은 개수가 아니라 분포 변화로 판단하도록 권고 |

### 부하 테스트 (2026-08-18)

배칭 상수와 처리 용량이 근거 없이 정해져 있고 목표 처리량이 정의된 적이 없어, 실측으로 목표를 정하고 한계를 측정했습니다. 상세는 [`AI/bench/REPORT.md`](https://github.com/jmkang21212-wq/S15P11C204/blob/feature/ai-load-bench/AI/bench/REPORT.md) (`feature/ai-load-bench` 브랜치).

1. **목표 산출**: 수집한 실제 방송 채팅(142세션 399만 건)에서 피크가 평균의 27~29배임을 확인. 방송마다 피크 시점이 달라 단순 합산하면 과대 추정되므로, 시계열을 무작위로 300회 겹쳐 **동시 방송 50개의 합산 피크 p95 = 227 TPS**를 목표로 정함
2. **병목 발견**: 기존 구성은 목표의 1/4(56 TPS)에서 이미 무너졌고, 서버 로그를 분해하니 원인은 추론이 아니라 대기였음. 동기 엔드포인트가 기본 스레드풀 40개로 CPU 2코어를 두고 경합하고 있었음
3. **개선**: 모델·CPU·추론 로직은 그대로 두고 설정 2개만 변경

| 구성 | 처리량 (목표 227 TPS) | 오류율 |
|---|---|---|
| 기존 (스레드풀 40 · fp32) | 12.9 TPS | 84.6% |
| 스레드풀 2 · fp32 | 98.9 TPS (7.7배) | 0% |
| **스레드풀 2 · int8** | **217.6 TPS (목표의 96%) · p99 895ms** | **0%** |

> 스레드풀만 줄였을 때 처리량은 목표의 44%에 그쳤습니다. int8은 처음에 "추론이 전체 지연의 1.5%라 효과가 없다"고 잘못 판단했다가, 포화 상태에서는 요청당 작업 시간이 처리량을 결정한다는 점을 확인하고 적용했습니다.
> 위 결과는 벤치 환경에서 측정한 값이며, 보고서의 권고(스레드풀 2, int8 전환)는 운영 설정에 반영하기 전 단계입니다.
