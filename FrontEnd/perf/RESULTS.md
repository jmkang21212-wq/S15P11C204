세 가지를 각각 재고 고쳤다. 전부 재현 가능한 하네스로 남겨 뒀고, B·C는 회귀하면 테스트가 깨진다.

## A. 공개 웹(`/discover`) 첫 로딩

### 측정 방법

Lighthouse 13을 `out/web` 빌드에 대해 돌린다. 프로덕션 nginx의 동작(자산 영구 캐시,
SPA 폴백, `/api` 응답)을 흉내 낸 정적 서버로 서빙하고, API는 고정 응답을 준다 —
화면이 실제 카드 목록으로 채워져야 LCP가 의미를 갖는다.

측정 조건을 두 가지로 나눴다.

- **simulate** — Lighthouse 기본값. 관측한 의존 그래프를 고정 네트워크 파라미터로 재계산해
  머신 부하에 거의 흔들리지 않는다(실행 간 FCP 편차 ±7ms). 다만 로컬 서버가 빨라 폰트가
  첫 페인트 전에 도착해 버려서, `font-display: swap`의 효과가 반영되지 않는 편향이 있다.
- **devtools(네트워크만)** — 브라우저에 실제 스로틀을 건다. swap 동작이 그대로 관측된다.
  CPU 스로틀(기본 4배)은 껐다 — 머신의 다른 부하까지 4배로 증폭해 TBT·TTI를 못 믿게 만든다.

두 조건 모두 **A/B를 한 회차마다 번갈아** 돌린다. 한쪽을 5회 몰아서 재고 다른 쪽을 5회 재는
방식은 실제로 편향을 만들었다 — 뒤에 돌린 쪽의 TBT가 실행을 거듭할수록 커졌다.

```bash
node ab.mjs --a http://localhost:4173/discover --b http://localhost:4178/discover \
            --labels before,after --preset mobile --throttling devtools --cpu 1 --rounds 7
```

### 결과 (중앙값)

| 지표 | before | after | 변화 |
|---|---:|---:|---:|
| **전송량 합계** | 1764.6kB | 486.3kB | **−72.4%** |
| ├ JS | 425.6kB | 120.7kB | −71.6% |
| ├ CSS | 72.8kB | 12.8kB | −82.4% |
| └ 폰트 | 1259.3kB | 349.8kB | −72.2% |
| FCP (simulate, 모바일) | 9913ms | 3358ms | **−66.1%** |
| LCP (simulate, 모바일) | 10063ms | 3610ms | −64.1% |
| 성능 점수 (simulate, 모바일) | 56 | 83 | +27 |
| FCP (실스로틀, 네트워크만) | 4518ms | 2440ms | **−46.0%** |
| Speed Index (실스로틀) | 3355ms | 1926ms | −42.6% |
| 성능 점수 (실스로틀) | 75 | 95 | +20 |
| 성능 점수 (simulate, 데스크톱) | 85 | 98 | +13 |

### 무엇을 고쳤나

**1. 폰트 서브셋 — 1259.3kB → 349.8kB (−72.2%)**

Wanted Sans Variable 원본은 한글 음절 11,172자를 전부 담아 1.26MB였고, 이 파일 하나가
공개 웹 전송량의 71%였다. KS X 1001 완성형 2,350자 + 라틴·기호만 남긴 서브셋을 만들어
기본 서체로 쓴다(`scripts/subset-font.mjs`).

커버리지는 폴백 패밀리로 유지한다.

```css
font-family: 'Wanted Sans Variable', 'Wanted Sans Variable Full', ...
```

브라우저가 문자 단위로 글리프 커버리지를 보고 고르므로, 서브셋에 있는 문자만 나오는 한
원본은 요청조차 되지 않는다. 실제로 확인했다 — `/discover`에서 원본의 폰트 상태는
`unloaded`로 남고, 서브셋에 없는 음절(`쀍뷁뜽쭹`)을 넣은 순간에만 원본 1.26MB를 받아 온다.

웹 빌드 산출물(`out/web`)에 실린 문자를 전부 서브셋 커버리지와 대조해 확인했다. 서브셋 밖
문자는 `react-router`가 라우트 예외 때 보여주는 내부 문구의 이모지 둘뿐이고, 정상 동작에서는
렌더되지 않는다. 즉 공개 웹의 고정 UI 문구는 서브셋으로 전부 덮인다.

`unicode-range`를 쓰지 않은 이유는 KS X 1001 2,350자가 1,613개 구간으로 흩어져 있어서다.
구간을 병합해 개수를 줄이려면 글리프가 급격히 늘어 서브셋의 의미가 사라진다.

| 병합 허용 간격 | 구간 수 | 포함 글리프 | CSS 바이트 |
|---:|---:|---:|---:|
| 0 | 1613 | 2350 | 14070 |
| 3 | 642 | 4235 | 6948 |
| 8 | 170 | 7185 | 1889 |

폴백 패밀리는 이 비용이 0이다.

**2. 데이터 라우터 → `BrowserRouter` — JS 435.6kB → 382.2kB**

공개 웹 라우터에는 loader·action이 하나도 없는데 `createBrowserRouter`를 참조하는 것만으로
데이터 라우터 런타임 전체가 번들에 들어왔다(react-router 88.3kB → 36.4kB).

**3. nginx gzip — 803.2kB → 486.3kB**

Ubuntu 기본 `nginx.conf`는 `gzip on`이지만 `gzip_types`가 주석 처리돼 있어 `text/html`만
압축된다. 즉 JS·CSS가 무압축으로 나가고 있었다. 이것만으로 FCP가 4111ms → 2423ms (−41.1%).

### 되돌린 것 — 라우트 코드 스플리팅

라우트별 `lazy()`도 넣었다가 뺐다. 초기 JS는 435.6kB → 374.1kB로 줄었는데, 청크는 index가
실행된 뒤에야 요청되므로 라운드트립이 한 번 더 붙는다. 느린 회선(RTT 150ms)에서 이 지연이
줄인 용량(61kB ≈ 305ms)보다 커서 **FCP가 오히려 250ms 느려졌다** — 7회 교차 측정 중 6회에서
재현됐다. 바이트가 줄었다는 이유만으로 개선이라고 볼 수 없다는 걸 이 건에서 확인했다.

공유 링크로 들어오는 `/p/:slug`는 Radix Select·floating-ui(약 60kB)를 안 써서 스플리팅
이득이 더 크지만(149kB), 기본 진입점인 `/discover`의 손해를 감수할 이유가 없어 함께 뺐다.

### 재현

```bash
pnpm build:web
node serve.mjs --dir <out/web> --port 4178 --gzip
node ab.mjs --a <before-url> --b <after-url> --labels before,after --preset mobile --rounds 5
```

측정 스크립트(`serve.mjs`·`ab.mjs`)는 저장소 밖 작업 디렉터리에 있다. 산출물 크기만 보려면
`pnpm build:web` 출력으로 충분하다.

## B. 방송 콘솔 리렌더 (`pnpm perf:console`)

콘솔은 방송 내내(보통 3~6시간) 세컨드 모니터에 떠 있고 3초마다 스냅샷을 다시 받는다.
응답은 매번 새로 파싱된 객체라 값이 그대로여도 참조가 달라지고, 그 결과 화면 전체가
3초마다 다시 렌더됐다. `memo`는 콘솔 컴포넌트에 하나도 없었다.

### 결과 — 20 tick 동안 각 패널이 실제로 렌더된 횟수

| 시나리오 | before | after | 변화 |
|---|---:|---:|---:|
| 스냅샷이 완전히 동일 | 320 | **0** | −100% |
| 세션 필드(경과·시청자)만 변경 — 실제 방송의 기본형 | 320 | **20** | −93.8% |
| 여론까지 변경 | 320 | **40** | −87.5% |

패널 8개 × 40 커밋 = 320이 기준선이다. 최적화 후에는 실제로 값이 바뀐 패널만 렌더된다
(세션 필드만 바뀌면 상태줄 하나, 여론까지 바뀌면 상태줄 + 여론 패널).

React Profiler `actualDuration` 합계도 63.5ms → 38.5ms(세션 필드 변경 기준)로 줄었지만,
이 값은 실행마다 흔들려서 렌더 횟수를 주 지표로 삼았다. 렌더 횟수는 5회 반복 모두 동일했다.

### 무엇을 고쳤나

1. **조각 단위 참조 유지** (`lib/reuseUnchanged.ts`) — 새 응답에서 값이 바뀌지 않은 최상위
   조각은 이전 참조를 그대로 물려준다. 최상위 키 단위로 비교하는 게 핵심이다. 실제 방송에서는
   `session.elapsedSeconds`가 매 tick 바뀌므로 **객체 전체를 한 덩어리로 비교하는 방식은
   아무것도 걸러내지 못한다.**
2. **패널 8개에 `memo`** — 1이 없으면 얕은 비교가 매번 깨져 효과가 없다.
3. **파생값 고정** — `mergeBriefings` 결과와 약속 상태 `Map`을 `useMemo`로, 인라인 핸들러
   두 개를 `useCallback`으로, `?? []`를 모듈 상수로 바꿨다.
4. **`useAudioStream` 반환 객체 고정** — 이 훅이 매 렌더 새 리터럴을 돌려주고 있어서,
   그 값을 prop으로 받는 `ConsoleStatusBar`의 `memo`는 실제 앱에서 항상 깨지고 있었다.
5. **`useCurrentSession`에도 같은 참조 유지 적용** — 이 값은 `ConsoleLayout`이 Outlet
   context로 콘솔에 내려주므로, 3초 폴링을 아무리 다듬어도 이쪽이 매번 새 객체이면 15초마다
   콘솔이 다시 렌더된다. 콘솔 하네스는 이 context를 고정 객체로 두어 이 경로를 재지 못하므로
   `perf/session-identity.test.tsx`로 따로 확인한다(수정 전 상태에서 실패하는 것까지 확인).

넷이 맞물려야 효과가 나고, 어느 하나가 풀려도 화면은 멀쩡해 보이고 렌더 수만 조용히
8배로 돌아간다. 그래서 하네스에 단언을 걸어 회귀하면 테스트가 깨지게 했다.

### 측정 하네스가 실제와 어긋났던 건

처음에는 `useAudioStream`을 고정 객체로 스텁했다. 그 상태의 측정값은 "세션 필드만 변경"에서
상태줄 20회였는데, 실제 훅은 매 렌더 새 객체를 돌려주므로 **실제 앱에서는 40회**였다.
하네스가 실제보다 유리한 수치를 낸 것이다.

그래서 이 훅은 모킹을 걷어내고 실제 구현을 그대로 쓰도록 바꾸고(WebSocket·AudioContext는
`start()`를 부를 때만 만들어져 jsdom에서도 안전하다), 훅 자체에 4번을 적용했다. 위 표의
수치는 그렇게 고친 뒤의 값이다. 기준선(320)도 같은 하네스로 다시 측정해 비교를 맞췄다.

### 기능이 그대로인지 — `perf/console-behavior.test.tsx`

리렌더 최적화는 잘못 걸면 화면이 조용히 갱신되지 않는 버그가 된다. 렌더 횟수만 세는
하네스로는 그걸 잡지 못하므로, 폴링으로 값이 바뀔 때 화면 텍스트가 실제로 바뀌는지를
DOM으로 확인하는 테스트를 따로 뒀다 — 시청자 수·열성 시청자·반복 질문·브리핑 추가,
그리고 값이 그대로일 때 화면도 그대로인지.

이 테스트에 실효성이 있는지도 확인했다. `reuseUnchanged`의 비교가 항상 "같다"를 반환하도록
버그를 주입하면 16건 중 8건이 실패한다.

## C. 창 간 스냅샷 릴레이 (`pnpm perf:console`)

방송 중에는 창이 최대 셋 뜬다 — 콘솔·미니 모드·OBS 오버레이. 셋 다 같은 스냅샷을 보여주는데,
각자 폴링하면 서버 요청이 창 수만큼 배로 늘고 3초 주기가 서로 어긋난 채 돌아 창끼리 값도
어긋난다. 콘솔 창만 owner로 폴링하고 나머지는 IPC 릴레이를 구독하도록 설계돼 있다.

대조군(창마다 독립 폴링)을 만들어 그 설계가 실제로 줄이는 양을 쟀다.

| 구성 | 창 | 20 tick 동안 API 호출 | 요청/시간 | 전송/시간 |
|---|---:|---:|---:|---:|
| 콘솔만 | 1 | 21 | 1260 | 3.0MB |
| 콘솔+미니 (독립 폴링) | 2 | 42 | 2520 | 6.1MB |
| **콘솔+미니 (릴레이)** | 2 | **21** | **1260** | **3.0MB** |
| 콘솔+미니+오버레이 (독립 폴링) | 3 | 63 | 3780 | 9.1MB |
| **3창 (릴레이)** | 3 | **21** | **1260** | **3.0MB** |

창이 늘어도 요청 수가 1창과 같다는 것, 그리고 창들이 같은 값을 보고 있다는 것을 단언으로
고정했다. 전송량은 이 하네스가 쓰는 합성 응답(2535B) 기준이다.

4시간 방송·3창 기준으로 환산하면 서버 요청 15,120회 → 5,040회다.
