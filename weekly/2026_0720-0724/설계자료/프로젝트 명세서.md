## 1. 개요

### 1.1 목적

본 문서는 1인 스트리머의 방송 준비·실시간 진행·방송 종료 후 분석 및 비즈니스 활동을 지원하는 **AI 매니저 웹 서비스**의 요구사항을 정의한다. 개발팀 전원이 동일한 기능 범위와 완료 기준을 공유하고, 설계·구현·테스트의 기준 문서로 사용하는 것을 목적으로 한다.

### 1.2 프로젝트 배경

1인 스트리머는 방송 진행 외에도 일정 관리, 콘텐츠 기획, 채팅 관리, 팬덤 소통, 광고·합방 협상 등 다수의 비방송 업무를 병행한다. 이 업무들은 대부분 수작업이며, 방송 중에는 물리적으로 동시 수행이 불가능하다. 본 서비스는 이 반복 업무를 AI가 보조하여 스트리머가 방송 콘텐츠 자체에 집중할 수 있도록 한다.

### 1.3 프로젝트 범위

**포함 범위 (In Scope)**

- 방송 전: 방송 시간대 추천, 콘텐츠·제목·썸네일 제안, 일정 캘린더, 공지 발행
- 방송 중: STT 기반 위험 발언 감지, 실시간 채팅 여론·반복 질문 요약, 약속 발언 추출
- 방송 후: 자동 리포트 생성(성장 리포트·로드맵), 하이라이트·쇼츠 클립 생성
- 비즈니스: 포트폴리오 확인 (프로필)
- 클라이언트: 웹(React) + 데스크탑(Electron) — **스트리머용 화면(대시보드·방송 콘솔·리포트·클립·포트폴리오 편집·매칭)은 Electron 앱으로 통합 제공**. 포트폴리오 공개 뷰(`/portfolio/{streamerId}`, 광고주·타 스트리머·시청자가 링크로 접근)만 별도 웹 라우트로 유지. React 코드베이스는 공용.

**제외 범위 (Out of Scope)**

- 실제 방송 송출(인코딩·스트리밍) 기능 — OBS 등 기존 도구를 사용한다
- 광고 대금 정산·결제 처리 — 매칭 및 이력 관리까지만 지원한다
- 영상 편집 툴 수준의 정밀 편집 — 자동 생성 클립의 다운로드까지 지원한다
- 모바일 네이티브 앱

### 1.4 용어 정의

| 용어 | 정의 |
| --- | --- |
| 스트리머 | 본 서비스의 주 사용자. 방송 계정을 연동한 회원 |
| 세션 | 방송 시작부터 종료까지의 1회 방송 단위 |
| 이벤트 | 방송 중 규칙 엔진이 탐지한 유의미한 상황 (위험 발언, 채팅 급증 등) |
| 브리핑 | 이벤트 발생 시 스트리머에게 전달되는 짧은 안내 문장 |
| 하이라이트 | 채팅 반응 급증 구간으로 탐지된 방송 구간 |
| 약속 | 방송 중 스트리머가 시청자에게 한 이행 대상 발언 |
| 열성 시청자 | 시청·채팅·후원 지표 기준 상위 시청자 |
| STT | Speech-to-Text, 음성의 텍스트 변환 |

### 1.5 참조 문서

- 팀 Git 컨벤션 및 코드 컨벤션 문서

## 3. 사용자 정의 및 권한

### 3.1 사용자 유형

| 유형 | 설명 | 주요 목표 |
| --- | --- | --- |
| 스트리머 (주 사용자) | 방송 계정을 연동한 개인 방송인 | 방송 준비 부담 감소, 성장 지표 확인, 수익 기회 확보 |
| 광고주 (부 사용자) | 광고 캠페인을 등록하는 기업 담당자 | 콘텐츠 성향에 맞는 스트리머 탐색 및 제안 |
| 관리자 | 서비스 운영자 | 회원·신고·매칭 요청 관리 |

### 3.2 페르소나

- **P1 — 성장기 게임 스트리머 (동시 시청자 50~300명)**
혼자 방송하며 채팅을 다 읽지 못한다. 실수 발언에 대한 불안이 크고, 광고 제안을 받아본 적이 없다.
- **P2 — 버추얼/토크 스트리머 (동시 시청자 300~1,000명)**
팬덤 관리 니즈가 크다. 시청자와의 약속을 자주 하지만 기억하지 못해 신뢰를 잃은 경험이 있다.
- **P3 — 중소 브랜드 마케터**
예산 대비 효율이 좋은 중소 스트리머를 찾고 싶지만 탐색 채널이 없다.

### 3.3 권한 매트릭스

| 기능 | 스트리머 | 광고주 | 관리자 |

| 실시간 브리핑 수신 | O | X | X |

## 4. 시스템 아키텍처

### 4.1 구성 개요

```
[Electron App · React]              [Browser · React]
   │  HTTPS / WebSocket                │  HTTPS
   │  (스트리머 전 화면: 대시보드·        │  (포트폴리오 공개 뷰만)
   │   방송 콘솔·미니모드·리포트·         │   광고주 · 타 스트리머 · 시청자
   │   클립·포트폴리오 편집·매칭)         │   링크 접근, 로그인 불필요
   ├── 로컬 오디오 캡처 → 청크 업로드     │
   └── obs-websocket (localhost) 연동   │
   ▼                                   ▼
[Nginx (Reverse Proxy, TLS)]
   │
   ├──────────────► [Spring Boot API Server]
   │                 - 인증/인가, 회원, 일정, 공지
   │                 - 포트폴리오, 광고/합방 매칭
   │                 - WebSocket 브리핑 브로커
   │                 - 방송 플랫폼 채팅 수집기
   │                        │
   │                        ├── PostgreSQL (영속 데이터)
   │                        ├── Redis (세션 캐시, 실시간 카운터, 큐)
   │                        └── S3 호환 스토리지 (음성/영상/클립)
   │
   └──────────────► [FastAPI AI Server]
                     - STT (Whisper)
                     - 위험 발언 분류 / 채팅 모더레이션
                     - 채팅 요약, 약속 추출
                     - 리포트 생성 (LLM)
                     - 하이라이트 탐지 + FFmpeg 클립 추출
```

### 4.2 서버 분리 원칙

- **Spring Boot**: 비즈니스 로직, 트랜잭션, 인증, 사용자 대면 API를 담당한다.
- **FastAPI**: 모델 추론과 미디어 처리 등 CPU/GPU 부하 및 지연이 큰 작업만 담당한다. 상태를 갖지 않으며, 결과는 콜백 또는 큐를 통해 Spring Boot로 반환한다.
- 두 서버 간 통신은 내부 네트워크의 REST + 공유 시크릿 헤더로 인증한다.

### 4.3 클라이언트 분리 원칙

- 스트리머가 로그인해서 쓰는 화면(대시보드·방송 콘솔·미니 모드·세션/성장 리포트·클립·포트폴리오 편집·비즈니스 매칭)은 전부 Electron 앱 하나로 제공한다. 반면 포트폴리오 공개 뷰(`GET /portfolio/{streamerId}`)는 광고주·타 스트리머·시청자가 링크만으로 접근해야 하므로 별도 웹 라우트로 남긴다 — 이 화면만 로그인·앱 설치 없이 열람 가능해야 한다. Electron 앱이 로컬 마이크 오디오를 캡처해 서버로 청크 업로드하며, 동일 앱이 obs-websocket을 통해 로컬 OBS 인스턴스와 통신한다.
- 인증 방식은 두 클라이언트가 동일(JWT)하되, 웹 라우트의 포트폴리오 공개 뷰는 인증 없이 조회 가능한 예외 엔드포인트로 취급한다(NFR-S-02와 별개로 명시 필요).

### 4.4 실시간 / 비동기 경로 분리

| 구분 | 경로 | 목표 지연 |
| --- | --- | --- |
| 실시간 | 채팅 수집 → Redis 카운터 → 규칙 엔진 → (필요 시) LLM 문장화 → WebSocket 푸시 | 5초 이내 |
| 실시간 | 음성 청크 → STT → 위험 발언 규칙 판별 → WebSocket 경고 | 10초 이내 |
| 비동기 | 방송 종료 → 작업 큐 등록 → 리포트 생성 / 하이라이트 추출 | 30분 이내 |

### 4.5 이벤트 기반 브리핑 동작 원칙

모든 채팅·발언에 대해 LLM을 호출하지 않는다. 1차로 규칙 엔진이 임계값 기반으로 이벤트를 판별하고, 이벤트가 발생한 경우에만 LLM이 코칭 문장으로 변환한다. 이는 비용·지연·소음(불필요한 알림)을 동시에 줄이기 위한 설계다.

## 5. 외부 연동 명세

| 연동 대상 | 용도 | 방식 | 확인 필요 사항 |
| --- | --- | --- | --- |
| 방송 플랫폼 (치지직/SOOP 등) | 채팅 수신, 시청자 수, 방송 메타 | OAuth + WebSocket/API | **API 정책 및 채팅 수집 허용 여부 사전 확인 필수** |
| LLM API | 요약, 리포트, 추천, 코칭 문장 생성 | HTTPS REST | 토큰 단가, RPM 제한, 개인정보 전송 정책 |
| Whisper (자체 호스팅 또는 API) | 음성 → 텍스트 | 로컬 추론 또는 REST | GPU 사양 / 실시간 처리 가능 여부 |
| FFmpeg | 클립·쇼츠 추출 | 로컬 프로세스 | 원본 영상 확보 경로 (VOD 다운로드 가능 여부) |
| 오브젝트 스토리지 | 음성·영상·클립 저장 | S3 API | 보관 기간 및 용량 정책 |
| **Electron 로컬 오디오 캡처** | STT 입력 음성 확보 | OS 마이크 API → 청크 단위 HTTPS 업로드 | 마이크 입력 장치 선택 UI 필요, 방송 믹서 오디오와 별도로 스트리머 음성만 잡는지 확인 |
| obs-websocket | 로컬 OBS 제어(추후 리플레이 버퍼 등 확장 여지) | localhost WebSocket | OBS 설치·플러그인 활성화 여부는 사용자 환경 의존 → 미설치 시 정상 동작(오디오 캡처와는 독립) |

> ⚠️ **최우선 리스크**: 방송 플랫폼의 채팅·VOD 접근 가능 여부가 확정되지 않으면 기능 다수가 성립하지 않는다. 착수 첫 주에 검증할 것.

### 6.2 주요 흐름

**방송 진행 흐름**

```
SC-02 대시보드 → [방송 시작 감지 또는 수동 시작]
  → SC-03 방송 콘솔 (실시간 브리핑 수신)
  → [방송 종료] → 비동기 분석 작업 등록
  → 완료 알림 → SC-06 리포트 → SC-07 클립
```

**비즈니스 흐름**

```
방송 실적 누적 → SC-10 포트폴리오 자동 갱신
→ SC-11 포트폴리오 공유 (프로필...)
```

## 8. 기능 상세 명세

MVP 기능에 대해 상세 정의한다. (나머지 기능은 동일 양식으로 확장한다.)

### FR-S-01 위험 발언 실시간 감지

| 항목 | 내용 |
| --- | --- |
| 선행 조건 | 방송 세션이 진행 중이며, Electron 앱이 로컬 마이크로부터 오디오를 캡처해 서버로 청크 업로드하고 있음 |
| 입력 | 오디오 청크(권장 10~15초), 스트리머별 민감도 설정 |
| 처리 | ① 청크를 STT로 변환 → ② 금칙어·패턴 사전으로 1차 판별 → ③ 애매한 경우에만 LLM 분류 호출 → ④ 위험도(HIGH/MEDIUM/LOW) 산출 |
| 출력 | WebSocket 브리핑 메시지 `{type, level, quote, timestamp, advice}` |
| 예외 | STT 실패 시 해당 청크 스킵 및 로그 기록, 3회 연속 실패 시 사용자에게 상태 표시 |
| 성능 기준 | 발언 종료 후 10초 이내 경고 노출 |
| 완료 기준 | 사전 정의 테스트 문장 20건 중 HIGH 항목 검출률 80% 이상 |

### FR-F-01 실시간 채팅 여론 요약

| 항목 | 내용 |
| --- | --- |
| 선행 조건 | 채팅 수집 소켓 연결됨 |
| 입력 | 최근 3분 채팅 메시지, 직전 요약본 |
| 처리 | ① Redis에 슬라이딩 윈도우 적재 → ② 메시지 수/감정 편향이 임계값 초과 시 이벤트 발생 → ③ LLM으로 1~2문장 요약 |
| 출력 | 여론 요약 문장, 분위기 지표(긍정/중립/부정 비율) |
| 예외 | 채팅량이 최소 임계값(예: 20건) 미만이면 요약을 생성하지 않음 |
| 성능 기준 | 이벤트 발생 후 5초 이내 노출 |
| 완료 기준 | 요약이 실제 채팅 화제와 일치한다고 평가자 3인 중 2인 이상이 판단 |

### FR-T-04 방송 자동 리포트

| 항목 | 내용 |
| --- | --- |
| 트리거 | 방송 세션 종료 이벤트 |
| 입력 | 시청자 수 시계열, 채팅 로그, STT 전문, 세션 메타 |
| 처리 | ① 유입/이탈 변곡점 산출 → ② 채팅 피크 구간 산출 → ③ 구간별 발언 매핑 → ④ LLM 요약 및 개선 제안 생성 |
| 출력 | 리포트 문서(요약, 지표 차트 데이터, 개선 제안 3건, 하이라이트 후보) |
| 성능 기준 | 3시간 방송 기준 3분 이내 생성 완료 |
| 예외 | 생성 실패 시 재시도 2회, 최종 실패 시 지표 리포트만 제공 |

### FR-R-01 하이라이트 구간 탐지

| 출력 | `[{start, end, score, reason}]` |

### FR-F-05 실시간 호응도 산출

| 항목 | 내용 |
| --- | --- |
| 선행 조건 | 채팅 수집 소켓 연결됨 |
| 입력 | 최근 N초 채팅 메시지(속도·이모티콘 비율) |

### 10.1 주요 엔티티

| 테이블 | 설명 | 핵심 컬럼 |

| `top_viewers` | 열성 시청자 | streamer_id, viewer_hash, score, period |
| `schedules` | 방송 일정 | streamer_id, start_at, end_at, type(방송/휴방), memo |
| `content_suggestions` | 콘텐츠 제안 | streamer_id, type, payload(jsonb), adopted |
| `portfolios` | 포트폴리오 | streamer_id, stats(jsonb), is_public |
| `campaigns` | 광고 캠페인 | advertiser_id, budget, target_tags, period |
| `collaborations` | 협업 이력 | streamer_id, counterpart_id, type(광고/합방), status |

### 10.2 설계 유의사항

- `chat_messages`, `viewer_metrics`는 세션당 수만~수십만 건이 쌓이므로 **세션 ID 기준 파티셔닝 또는 보관 기간(예: 90일) 정책**을 적용한다.
- 시청자 식별자는 원본 대신 **해시값(`viewer_hash`)으로 저장**하여 개인정보 노출을 최소화한다.
- 플랫폼 토큰은 반드시 암호화하여 저장한다.
- 실시간 카운터·슬라이딩 윈도우는 PostgreSQL이 아닌 **Redis**에서 처리한다.

## 11. AI 파이프라인 명세

| 기능 | 입력 | 처리 방식 | 모델/도구 | 출력 | 지연 목표 |
| --- | --- | --- | --- | --- | --- |
| STT | 오디오 청크 | 스트리밍 추론 | Whisper (small/medium) | 텍스트 + 타임스탬프 | 청크당 3초 이내 |
| 위험 발언 분류 | STT 텍스트 | 사전 규칙 → 애매 시 LLM | 금칙어 사전 + LLM | 카테고리, 위험도 | 2초 이내 |
| 채팅 모더레이션 | 채팅 메시지 | 규칙 → 분류 모델 | 정규식 + 경량 분류기 | 조치 유형 | 500ms 이내 |
| 채팅 요약 | 3분 윈도우 | 이벤트 트리거 시 LLM | LLM API | 요약문, 분위기 지표 | 3초 이내 |
| 반복 질문 추출 | 채팅 배치 | 임베딩 클러스터링 | 임베딩 + 유사도 | 상위 질문 목록 | 3초 이내 |
| 약속 추출 | STT 전문 | 패턴 필터 → LLM 판별 | LLM | 약속 문장·기한 | 비동기 |
| 리포트 생성 | 세션 전체 데이터 | 통계 산출 → LLM 서술화 | 통계 + LLM | 리포트 본문 | 30분 이내 |
| 하이라이트 탐지 | 채팅 시계열 | z-score 이상치 탐지 | 규칙 기반 | 구간 목록 | 5분 이내 |
| 클립 생성 | 구간 + 원본 영상 | 컷 편집·크롭·자막 | FFmpeg | mp4 파일 | 구간당 2분 이내 |
| 추천(시간/콘텐츠) | 과거 실적·트렌드 | 통계 집계 → LLM 서술 | 통계 + LLM | 추천 3~5안 | 10초 이내 |

**프롬프트 관리 원칙**: 모든 LLM 프롬프트는 버전 관리 대상이며, 출력은 JSON 스키마로 강제하고 파싱 실패 시 1회 재시도 후 폴백 문구를 사용한다.
