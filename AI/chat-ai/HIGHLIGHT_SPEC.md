# 하이라이트 트리거 알고리즘 명세

> 대상: **백엔드** (Spring에서 구현)
> AI 서버 호출 규격은 [CHAT_AI_API.md](../CHAT_AI_API.md) 참고. 이 문서는 호출이 아니라
> **Spring 내부에 구현할 판정 로직**의 명세다.

채팅이 평소보다 얼마나 달아올랐는지를 통계로 감지해 하이라이트 구간
[시작, 끝]을 확정한다. **ML이 필요 없다** — 순수 산수라 Java로 그대로 구현된다.

---

## 0. 왜 /ingest 응답의 engagement를 쓰면 안 되나

AI 서버가 `/ingest` 응답에 engagement를 주지만, **하이라이트 판정 입력으로 쓰면
안 된다.** 이유 두 가지:

1. **가용성** — 그걸 쓰면 AI 서버가 죽는 순간 하이라이트도 죽는다.
   "AI 장애가 채팅 기능을 무너뜨리면 안 된다"는 우리 설계 원칙이 깨진다.
2. **반응 속도** — /ingest의 윈도우는 여론 요약용 180초라 둔하다.
   하이라이트 감지는 60초 윈도우로 민감하게 잡아야 시작점이 안 밀린다.

Spring은 이미 uid와 시청자 수를 갖고 있으므로 아래 계산을 자체 수행한다.

## 1. 지표 정의

1초마다(틱) 계산한다:

```
uniq(t)       = 최근 60초 안에 채팅 친 서로 다른 uid 수
engagement(t) = uniq(t) / viewers(t)          # 시청자의 몇 %가 최근 1분 내 채팅했나
```

시청자 수로 나누므로 채널 규모와 무관하다 — 500명 방도 5만 명 방도 같은 자로 잰다.
(절대 채팅량 임계치를 쓰면 소형 채널은 영원히 하이라이트가 안 잡힌다)

**유니크 채터 슬라이딩 윈도우** — O(1) 증분 계산 (매 틱 전체 재계산 금지):

```
deque<(ts, uid)> window          # 시간순
Map<uid, int>    count           # uid → 윈도우 내 등장 횟수

채팅 수신:   window.push(ts, uid);  count[uid]++
매 틱 정리:  while window.front.ts < now - 60s:
                (ts, uid) = window.pop_front()
                if --count[uid] == 0: count.remove(uid)
uniq = count.size()
```

count가 Map<uid, **횟수**>인 이유: 같은 사람의 옛 채팅 하나가 윈도우를 빠져도
그 사람의 다른 채팅이 남아 있으면 유니크에서 빼면 안 된다. 횟수가 0이 되는
순간에만 사람이 빠진다.

## 2. "평소 대비 얼마나 튀는가" — z-score

**평균·표준편차가 아니라 median·MAD를 쓴다.** 하이라이트 자체가 극단값이라,
평균·표준편차는 하이라이트가 낄 때마다 baseline이 오염되어 다음 감지가 무뎌진다.
median·MAD는 극단값에 강건하다.

```
baseline = 최근 15분(900개)의 engagement 값들     # 링버퍼
med      = median(baseline)
mad      = median(|x - med| for x in baseline)
z(t)     = (engagement(t) - med) / (1.4826 × mad)   # 1.4826: 정규분포 보정 상수
```

## 3. 상태기계

```
                z ≥ Z_ENTER 가 ENTER_TICKS 연속
   ┌────────┐ ─────────────────────────────────▶ ┌────────┐
   │  IDLE  │                                    │ ACTIVE │
   └────────┘ ◀───────────────┐                  └───┬────┘
        ▲                     │                      │ z ≤ Z_EXIT 가 EXIT_TICKS 연속
        │              ┌──────┴─────┐               │ 또는 MAX_ACTIVE 경과 (강제 확정)
        └──────────────│  COOLDOWN  │◀──────────────┘
          COOLDOWN 경과 └────────────┘   구간 확정 → 저장
```

전이 규칙:

| 전이 | 조건 | 동작 |
|---|---|---|
| IDLE → ACTIVE | `z ≥ 3.0`이 **3틱 연속** | `start = 현재시각 − 30초` (리드: 달아오르기 시작한 순간을 소급) |
| ACTIVE → 확정 | `z ≤ 1.5`가 **15틱 연속** | `end = 이탈 첫 틱 시각`. 저장 후 COOLDOWN |
| ACTIVE → 강제 확정 | 지속 **5분** 초과 | 그 시점으로 확정 (러닝 하이라이트 방지) |
| COOLDOWN → IDLE | **30초** 경과 | — |

진입(3.0)과 이탈(1.5) 임계가 다른 이유(히스테리시스): 같은 값이면 경계에서
z가 진동할 때 하이라이트가 잘게 쪼개진다.

**확정 시 저장할 것:**

```
broadcastId, startedAt, endedAt,
peakZ, peakEngagement, avgViewers,
chatCount(구간 내), uniqueChatters(구간 내)
```

구간 내 채팅·감정 통계는 Spring이 자체 저장한 원본(+/ingest가 돌려준 건별 감정)을
`startedAt ≤ ts ≤ endedAt`으로 조회하면 된다.

## 4. 가드 (없으면 반드시 오탐/장애 난다)

| # | 상황 | 규칙 |
|---|---|---|
| 1 | **워밍업** | 방송 시작 후 3분간 판정 금지. baseline이 없고, 시작 직후 "안녕하세요" 러시가 전부 잡힌다 |
| 2 | **MAD = 0** | 채팅 패턴이 균일하면 mad=0 → z가 무한대. `mad = max(mad, ε)` (ε = 0.001 권장) |
| 3 | **저활동** | 60초 윈도우 채팅 10건 미만이면 그 틱은 판정 생략. 심야 유휴 채널에서 2~3명이 떠들면 z가 튄다 |
| 4 | **시청자 결측** | 폴링 실패 시 마지막 정상값 사용(최대 5분). 그것도 없으면 판정 생략. **0으로 나누지 말 것** |
| 5 | **방송 종료 시 ACTIVE 중** | 종료 시각으로 강제 확정하고 저장 (마지막 하이라이트 유실 방지) |
| 6 | **강제 확정 직후에도 뜨거움** | COOLDOWN 후 새 구간으로 분리 저장. 인접 구간(간격 < 1분) 병합 여부는 조회 시점에 결정해도 됨 |
| 7 | **서버 재시작** | baseline 15분이 비면 워밍업부터 다시. Redis에 engagement 시계열을 남겨뒀다면 복원해서 워밍업 생략 가능 (선택) |
| 8 | **시계** | 모든 시각은 서버 수신 시각 기준. 치지직 msgTime은 클라이언트 시계라 신뢰하지 말 것 |

## 5. 파라미터 (초기값 — 반드시 튜닝 전제)

| 파라미터 | 초기값 | 올리면 | 내리면 |
|---|---|---|---|
| `ENGAGE_WINDOW` | 60초 | 둔감, 안정 | 민감, 노이즈 |
| `BASELINE` | 15분 | 느린 적응 | 하이라이트가 baseline을 금방 오염 |
| `Z_ENTER` | 3.0 | 놓침 증가 | 오탐 증가 |
| `ENTER_TICKS` | 3 | 시작 감지 지연 | 순간 스파이크 오탐 |
| `Z_EXIT` | 1.5 | 구간 짧아짐 | 구간 늘어짐 |
| `EXIT_TICKS` | 15 | 구간 이어붙음 | 잘게 쪼개짐 |
| `LEAD` | 30초 | 시작점 과소급 | 도입부 잘림 |
| `MAX_ACTIVE` | 5분 | — | — |
| `COOLDOWN` | 30초 | 연속 하이라이트 병합 효과 | 쪼개짐 |

**⚠ 이 값들은 이론과 소규모 관찰로 정한 초기값이지, 백테스트로 검증된 값이
아니다.** 운영 초기에 다음 두 값을 로그로 남길 것을 강권한다:

```
매 틱: (ts, engagement, z, state)      # 하루치면 판정 품질이 눈에 보인다
```

실제 방송 몇 회 로그를 보고 Z_ENTER/EXIT부터 조정하면 된다. 검출이 너무 많으면
Z_ENTER↑, 시작이 늦게 잡히면 ENTER_TICKS↓ 또는 LEAD↑.

## 6. 동작 예시 (타임라인)

```
시각    engagement   z     상태
10:00   0.08        0.2   IDLE          (평소)
10:05   0.09        0.5   IDLE
10:07   0.19        3.4   IDLE (1/3)    ← 사고 발생, 채팅 급증
10:07+1 0.21        3.9   IDLE (2/3)
10:07+2 0.22        4.1   ACTIVE 진입!  start = 10:06:32 (30초 리드)
10:09   0.31        5.2   ACTIVE        (peakZ 갱신)
10:11   0.12        1.4   ACTIVE (1/15) ← 식기 시작
  ...15틱 연속 z ≤ 1.5...
10:11+15 확정: [10:06:32 ~ 10:11:00], peakZ 5.2 → 저장 → COOLDOWN(30s) → IDLE
```
