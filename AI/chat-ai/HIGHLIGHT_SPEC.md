# 하이라이트 트리거 알고리즘 명세

> 대상: **백엔드** (Spring에서 구현)
> AI 서버 호출 규격은 [CHAT_AI_API.md](../CHAT_AI_API.md) 참고. 이 문서는 호출이 아니라
> **Spring 내부에 구현할 판정 로직**의 명세다.

채팅이 평소보다 얼마나 달아올랐는지를 통계로 감지해 하이라이트 구간
[시작, 끝]을 확정한다. **ML이 필요 없다** — 순수 산수라 Java로 그대로 구현된다.

---

## 0. 왜 /ingest 응답의 engagement를 쓰면 안 되나

AI 서버가 `/ingest` 응답에 engagement를 주지만, **하이라이트 판정 입력으로 쓰면
안 된다.** 이유 두 가지:

1. **가용성** — 그걸 쓰면 AI 서버가 죽는 순간 하이라이트도 죽는다.
   "AI 장애가 채팅 기능을 무너뜨리면 안 된다"는 우리 설계 원칙이 깨진다.
2. **반응 속도** — /ingest의 윈도우는 여론 요약용 180초라 둔하다.
   하이라이트 감지는 60초 윈도우로 민감하게 잡아야 시작점이 안 밀린다.

Spring은 이미 uid와 시청자 수를 갖고 있으므로 아래 계산을 자체 수행한다.

## 1. 지표 정의

1초마다(틱) 계산한다:

```
uniq(t)       = 최근 60초 안에 채팅 친 서로 다른 uid 수
engagement(t) = uniq(t) / viewers(t)          # 시청자의 몇 %가 최근 1분 내 채팅했나
```

시청자 수로 나누므로 채널 규모와 무관하다 — 500명 방도 5만 명 방도 같은 자로 잰다.
(절대 채팅량 임계치를 쓰면 소형 채널은 영원히 하이라이트가 안 잡힌다)

**유니크 채터 슬라이딩 윈도우** — O(1) 증분 계산 (매 틱 전체 재계산 금지):

```
deque<(ts, uid)> window          # 시간순
Map<uid, int>    count           # uid → 윈도우 내 등장 횟수

채팅 수신:   window.push(ts, uid);  count[uid]++
매 틱 정리:  while window.front.ts < now - 60s:
                (ts, uid) = window.pop_front()
                if --count[uid] == 0: count.remove(uid)
uniq = count.size()
```

count가 Map<uid, **횟수**>인 이유: 같은 사람의 옛 채팅 하나가 윈도우를 빠져도
그 사람의 다른 채팅이 남아 있으면 유니크에서 빼면 안 된다. 횟수가 0이 되는
순간에만 사람이 빠진다.

## 2. "평소 대비 얼마나 튀는가" — z-score

**평균·표준편차가 아니라 median·MAD를 쓴다.** 하이라이트 자체가 극단값이라,
평균·표준편차는 하이라이트가 낄 때마다 baseline이 오염되어 다음 감지가 무뎌진다.
median·MAD는 극단값에 강건하다.

```
baseline = 최근 15분(900개)의 engagement 값들     # 링버퍼
med      = median(baseline)
mad      = median(|x - med| for x in baseline)
mad_eff  = max(mad, ε, MAD_FLOOR_CHATTERS / viewers)   # 가드 2 — 하한
z(t)     = (engagement(t) - med) / (1.4826 × mad_eff)  # 1.4826: 정규분포 보정 상수
```

**MAD 하한이 2단인 이유** — 소규모 채널은 baseline이 같은 값(대개 0)으로
도배되어 MAD가 0으로 붕괴한다. 절대 하한 ε=0.001만으로는 시청자 5명 채널에서
채터 +1명(engagement +0.2)에 z≈135가 되어 Z_ENTER가 변별력을 잃는다.
`MAD_FLOOR_CHATTERS / viewers`는 하한을 **채터 수 단위**로 잡아 규모 불변으로
만든다: 하한이 지배할 때 진입에 필요한 초과분은 채널 규모와 무관하게

```
Z_ENTER × 1.4826 × MAD_FLOOR_CHATTERS ≈ 3.0 × 1.4826 × 0.5 ≈ 유니크 채터 +2.2명
```

즉 어떤 규모의 채널이든 "median 대비 2~3명이 더 떠들면" 진입 후보가 된다.
조용한 5명 채널에서 2명의 대화(z≈2.7)는 걸러지고 3명의 동시 반응(z≈4.05)은
잡힌다.

## 3. 상태기계

```
                z ≥ Z_ENTER 가 ENTER_TICKS 연속
   ┌────────┐ ─────────────────────────────────▶ ┌────────┐
   │  IDLE  │                                    │ ACTIVE │
   └────────┘ ◀───────────────┐                  └───┬────┘
        ▲                     │                      │ z ≤ Z_EXIT 가 EXIT_TICKS 연속
        │              ┌──────┴─────┐               │ 또는 MAX_ACTIVE 경과 (강제 확정)
        └──────────────│  COOLDOWN  │◀──────────────┘
          COOLDOWN 경과 └────────────┘   구간 확정 → 저장
```

전이 규칙:

| 전이 | 조건 | 동작 |
|---|---|---|
| IDLE → ACTIVE | `z ≥ 3.0`이 **3틱 연속** | `start = 현재시각 − 30초` (리드: 달아오르기 시작한 순간을 소급) |
| ACTIVE → 확정 | `z ≤ 1.5` 또는 **저활동(가드 3)** 틱이 **8틱 연속** | `end = 이탈 첫 틱 시각`. 저장 후 COOLDOWN |
| ACTIVE → 강제 확정 | 지속 **4분** 초과 | 그 시점으로 확정 (러닝 하이라이트 방지) |
| COOLDOWN → IDLE | **30초** 경과 | — |

이탈 카운트의 3원 의미론: **정상 이탈 틱(z ≤ Z_EXIT)과 저활동 틱은 같은
스트릭을 공유**하고(저활동은 "채팅이 죽었다"는 적극적 신호다 — 없으면 소규모
채널에서 급증이 끝나도 판정 가능한 틱이 없어 구간이 MAX_ACTIVE까지 늘어진다),
z > Z_EXIT인 정상 틱만 스트릭을 리셋하며, 판정 불가 틱(워밍업·시청자 결측·
수집 공백)은 기권이다(연장도 리셋도 안 함).

진입(3.0)과 이탈(1.5) 임계가 다른 이유(히스테리시스): 같은 값이면 경계에서
z가 진동할 때 하이라이트가 잘게 쪼개진다.

**확정 시 저장할 것:**

```
broadcastId, startedAt, endedAt,
peakZ, peakEngagement, avgViewers,
chatCount(구간 내), uniqueChatters(구간 내)
```

구간 내 채팅·감정 통계는 Spring이 자체 저장한 원본(+/ingest가 돌려준 건별 감정)을
`startedAt ≤ ts ≤ endedAt`으로 조회하면 된다.

## 4. 가드 (없으면 반드시 오탐/장애 난다)

| # | 상황 | 규칙 |
|---|---|---|
| 1 | **워밍업** | 방송 시작 후 3분간 판정 금지. baseline이 없고, 시작 직후 "안녕하세요" 러시가 전부 잡힌다. baseline 적재는 워밍업 중에도 계속한다(워밍업의 목적이 baseline 채우기다). 단 `BASELINE_DURING_WARMUP=false`면 워밍업 표본을 버리고 **워밍업 안에 받은 채팅을 판정 윈도우에서도 뺀다**(윈도우가 러시를 최대 `ENGAGE_WINDOW`만큼 물고 나와 첫 baseline 표본을 러시 수준으로 시드하는 것 방지) — 방송이 짧아 러시가 초기 baseline의 다수를 차지하면 median이 러시 수준으로 선점되어 이후 급증이 묻히는데(median의 강건함은 러시가 표본의 절반 미만일 때만 지켜준다), 이를 막는 시연·단방송용 옵션이다. 끄면 판정이 거의 빈 baseline으로 시작하므로 운영 기본은 true |
| 2 | **MAD = 0** | 채팅 패턴이 균일하면 mad=0 → z가 무한대. `mad = max(mad, ε, MAD_FLOOR_CHATTERS / viewers)` — 절대 하한 ε(0.001)에 더해 채터 수 단위 동적 하한을 둔다(§2). 심야 유휴 채널에서 2~3명이 떠들 때 z가 튀는 것도 이 하한이 막는다 |
| 3 | **저활동** | 60초 윈도우 채팅 4건 미만이면 그 틱은 정상 판정을 생략한다. 단 **ACTIVE 중에는 이탈 카운트에 산입**한다(§3) — 저활동은 정보 부재가 아니라 채팅 사멸의 신호다. IDLE에서는 동결. 절대량 노이즈 방어는 가드 2의 동적 하한이 맡으므로 이 값은 통계 안정성(표본 최소치)만 지키면 된다 |
| 4 | **시청자 결측** | 폴링 실패 시 마지막 정상값 사용(최대 5분). 그것도 없으면 판정 생략. **0으로 나누지 말 것**. 수신된 값에는 `viewers = max(viewers, 윈도우 uniq)`를 적용한다 — 치지직 시청자 집계는 실제 입장보다 1분 이상 늦어 소규모 방송에서 채터가 분모보다 먼저 늘면 engagement가 1.0을 넘는 지연 아티팩트가 baseline을 선점한다(2026-08-07 실측). 같은 이유로 채팅이 있는데 집계가 0인 틱은 zero-viewers로 쉬지 않고 판정한다 |
| 5 | **방송 종료 시 ACTIVE 중** | 종료 시각으로 강제 확정하고 저장 (마지막 하이라이트 유실 방지) |
| 6 | **강제 확정 직후에도 뜨거움** | COOLDOWN 후 새 구간으로 분리 저장. 인접 구간(간격 < 1분) 병합 여부는 조회 시점에 결정해도 됨 |
| 7 | **서버 재시작** | baseline 15분이 비면 워밍업부터 다시. Redis에 engagement 시계열을 남겨뒀다면 복원해서 워밍업 생략 가능 (선택) |
| 8 | **시계** | 모든 시각은 서버 수신 시각 기준. 치지직 msgTime은 클라이언트 시계라 신뢰하지 말 것 |
| 9 | **수집 중단** | `collection_gaps`에 걸친 틱은 판정에서 제외하고 **baseline에도 넣지 않는다** |

가드 9를 빼면 안 되는 이유: 치지직 socket.io는 자동 재연결이 되지 않아
재핸드셰이크 동안 채팅이 유실된다. 그 구간에 `uniq`가 0으로 떨어지면 15분
baseline에 인위적으로 낮은 값이 채워지고 **복구 직후의 정상 채팅이 급증으로
오탐된다.** median·MAD가 극단값에 강건하다는 2절의 전제는 공백이 없다는 가정에
기대고 있다 — 공백은 "튀는 값 하나"가 아니라 baseline 전체를 끌어내리는 구간이라
강건성이 막아주지 못한다.

공백 구간은 수집기가 `POST /internal/v1/sessions/{id}/collection-gaps`로 보고하며
`collection_gaps(session_id, started_at, ended_at)`에 쌓인다(V9). `ended_at`이
`NULL`인 행은 아직 복구되지 않은 진행 중 공백이다.

시계 주의(가드 8과의 관계): `chat_messages.sent_at`은 `messageTime`(클라이언트
시계)이지만 판정 틱은 서버 수신 시각으로 돈다. 두 축을 섞어 비교하지 말 것.

## 5. 파라미터 (초기값 — 반드시 튜닝 전제)

| 파라미터 | 초기값 | 올리면 | 내리면 |
|---|---|---|---|
| `ENGAGE_WINDOW` | 60초 | 둔감, 안정 | 민감, 노이즈 |
| `BASELINE` | 15분 | 느린 적응 | 하이라이트가 baseline을 금방 오염 |
| `Z_ENTER` | 3.0 | 놓침 증가 | 오탐 증가 |
| `ENTER_TICKS` | 3 | 시작 감지 지연 | 순간 스파이크 오탐 |
| `Z_EXIT` | 1.5 | 구간 짧아짐 | 구간 늘어짐 |
| `EXIT_TICKS` | 8 | 구간 이어붙음 | 잘게 쪼개짐 |
| `LEAD` | 30초 | 시작점 과소급 | 도입부 잘림 |
| `MAX_ACTIVE` | 4분 | LEAD 포함 300초 초과 시 리포트 자격 탈락 | — |
| `COOLDOWN` | 30초 | 연속 하이라이트 병합 효과 | 쪼개짐 |
| `MIN_WINDOW_CHATS` | 4 | 소규모 채널 판정 불가(구간 늘어짐 재발) | 표본 부족으로 z 불안정 |
| `BASELINE_DURING_WARMUP` | true | (기본) 워밍업이 baseline을 채워 판정 시작이 안정 | false: 인사 러시의 baseline 선점 방지(가드 1). 초반 z 불안정 |
| `MAD_FLOOR_CHATTERS` | 0.5 | 소규모 채널 둔감 | MAD 붕괴 시 오탐(2명 대화도 진입) |

`MAX_ACTIVE`는 강제 확정 구간 길이가 `MAX_ACTIVE + LEAD`가 되는 점에 주의 —
리포트 하이라이트 자격 상한(300초, `DeterministicHighlightGenerator`)을 넘지
않게 잡아야 한다. 4분 + 30초 = 270초.

**⚠ 이 값들은 이론과 소규모 관찰로 정한 초기값이지, 백테스트로 검증된 값이
아니다.** 운영 초기에 다음 두 값을 로그로 남길 것을 강권한다:

```
매 틱: (ts, engagement, z, state)      # 하루치면 판정 품질이 눈에 보인다
```

실제 방송 몇 회 로그를 보고 Z_ENTER/EXIT부터 조정하면 된다. 검출이 너무 많으면
Z_ENTER↑, 시작이 늦게 잡히면 ENTER_TICKS↓ 또는 LEAD↑.

## 6. 동작 예시 (타임라인)

```
시각    engagement   z     상태
10:00   0.08        0.2   IDLE          (평소)
10:05   0.09        0.5   IDLE
10:07   0.19        3.4   IDLE (1/3)    ← 사고 발생, 채팅 급증
10:07+1 0.21        3.9   IDLE (2/3)
10:07+2 0.22        4.1   ACTIVE 진입!  start = 10:06:32 (30초 리드)
10:09   0.31        5.2   ACTIVE        (peakZ 갱신)
10:11   0.12        1.4   ACTIVE (1/8)  ← 식기 시작
  ...8틱 연속 z ≤ 1.5 (저활동 틱도 이탈 표로 산입)...
10:11+8 확정: [10:06:32 ~ 10:11:00], peakZ 5.2 → 저장 → COOLDOWN(30s) → IDLE
```
