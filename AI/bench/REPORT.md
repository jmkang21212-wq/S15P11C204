# chat-ai 유량 실측 및 부하 한계 측정

> 측정일 2026-08-18 · 브랜치 `feature/ai-load-bench`
> 배경: 배칭 상수와 처리 용량이 **근거 없이 정해져 있었고**, 목표 TPS가 정의된 적이 없어
> 현재 구조가 실사용 부하를 버티는지 알 수 없는 상태였다.

## 결론 요약

| | 처리량 | p99 지연 | 오류율 |
|---|---|---|---|
| 기존 구성 (스레드풀 40 · fp32) | 12.9 TPS | 10,586ms | 84.6% |
| **스레드풀 2 · int8** | **217.6 TPS** | **895ms** | **0%** |

**목표 227 TPS를 96% 달성했고 Spring 계약 타임아웃(2초) 안에 들어온다. 개선 17배.**
설정 두 줄이고 추론 로직은 한 줄도 바뀌지 않았다. 한계는 약 **260 TPS**.

---

## 0. 시작 전 전제 정정

계획 단계의 전제와 실제 코드가 달랐다. 이걸 먼저 맞추지 않았으면 엉뚱한 곳을 계측할 뻔했다.

| 전제 | 실제 |
|---|---|
| asyncio 큐 마이크로배칭 100ms / 32건 | **없음.** 수집기는 `threading`+`queue.Queue`, 100건 or 1.0초 |
| chat-ai가 큐로 배칭 | `def ingest`는 **동기 엔드포인트**. 큐 없음 |
| 배치 크기 32 | `DEFAULT_BATCH=32`는 `predict()`가 ONNX에 넣을 때 쓰는 청크 크기 |
| int8 양자화 | **꺼져 있었음** (`CHATAI_INT8` 기본 0). fp32로 운영 중 |
| 수집기 → AI 서버 | 수집기 → **Spring** → chat-ai |

## 1단계: 실제 방송 채팅 유량

### 측정 조건

- 수집된 jsonl **오프라인 분석**. 서버 계측 코드 0줄 → 오버헤드 없음, 재현 가능
- 라이브 수신분 `chats_*` 20파일 156MB → **주 분석** (`_received_at`=우리가 받은 시각, `mbrCnt`=시청자)
- VOD 수집분 `vod_chats_*` 118파일 5.2GB → **보조** (표본 33배)
- 방송 구분: 채팅 공백 300초 이상이면 다른 방송
- 도구: `flow_stats.py`

### 결과

| 지표 | live (13세션 12만건) | vod (142세션 **399만건**) |
|---|---|---|
| 평균 TPS p50 | 0.203 | 0.208 |
| 피크 TPS p50 / max | 6 / 41 | 6 / 37 |
| **피크/평균 배수 p50** | **28.7** | **27.2** |
| 피크 지속 p50 / **max** | 12s / 22s | 10s / **73s** |
| 메시지 길이 p50 / p95 | 7 / 40자 | 7 / 32자 |
| 피크 TPS / 시청자 1천명 p95 | **43.7** | (시청자 데이터 없음) |

**표본 33배로 교차 검증되었다.** 중앙값이 거의 일치(0.203 vs 0.208, 배수 28.7 vs 27.2)해
라이브 20파일 표본이 우연이 아님을 확인했다. 다만 **꼬리는 라이브가 놓쳤다** — 피크 지속이
22초가 아니라 최대 **73초**다. 22초 스파이크는 버퍼로 흡수 가능하지만 73초는 불가능하다.

**피크가 평균의 27~29배**라는 것이 이번 실측의 핵심이다. 평균으로 용량을 잡으면 반드시 무너진다.

### 목표 부하 산출

방송별 피크를 단순 합산하면 안 된다. **방송마다 하이라이트 시점이 달라 피크가 동시에 오지 않는다.**
시계열 117개를 무작위로 300회 겹쳐 합산 피크를 구했다.

| 동시 방송 | 합산 피크 p50 | **p95** | max | 단순합(41×N) |
|---|---|---|---|---|
| 10개 | 64 | 95 | 117 | 410 |
| 20개 | 93 | 132 | 148 | 820 |
| **50개** | 177 | **227** | 261 | 2,050 |

**→ 목표 부하 확정: 227 TPS, 73초 지속.** 단순합으로 잡았으면 9배 과대설정할 뻔했다.

합산 피크가 난 1초의 실제 분포는 균등하지 않다: 최다 방송 30건, 상위 5개가 45%,
**절반(24개)은 0건**. 부하 스크립트는 이를 균등 배분으로 근사했다(5절 한계 참조).

## 2단계: chat-ai 부하 한계

### 측정 조건

- 부하 형태: **방송 50개 × 1초에 1요청** (CHAT_AI_API.md 계약. 채팅 없는 초에도 `RealtimeTicker`가 빈 배치 전송)
- 메시지: 실제 채팅 본문 2만 건에서 표본 추출. **합성 금지** — 길이 분포가 패딩·추론시간을 좌우한다
- 서버: ORT 2스레드 / **CPU 2코어** / GMS_KEY 비움(외부 호출 0)
- 단계: 목표의 0.25 / 0.5 / 1 (/ 2)배, 각 20초
- 도구: `load_ingest.py`(클라이언트) + `parse_access.py`(서버 로그)
- 판정: `p99 > 2초` / `처리량 포화` / `오류율 상승` 셋을 모두 기록하고 먼저 걸리는 것

### 클라이언트 측 결과

| 목표 | 스레드풀 40 · fp32 | 스레드풀 4 · fp32 | 스레드풀 2 · fp32 | **스레드풀 2 · int8** |
|---|---|---|---|---|
| 56 TPS | 27.2 · 7,634ms | 45.5 · 1,627ms | 52.8 · 582ms | **54.9 · 242ms** |
| 113 TPS | 42.6 · 9,167ms | 74.5 · 5,579ms | 78.9 · 4,652ms | **110.2 · 358ms** |
| **227 TPS** | 12.9 · 오류 84.6% | 38.4 · 오류 57.2% | 98.9 · 8,891ms | **217.6 · 472ms · 오류 0%** |
| 454 TPS | — | — | — | 262.6 · 6,407ms |

**기존 구성은 목표의 1/4인 56 TPS에서 이미 무너져 있었다.** 오류율 0%라 겉으로는 정상처럼
보였고, `completed_tps`(200으로 끝난 양 ÷ 전체 소요시간)를 봐야 드러났다.
부하를 올릴수록 처리량이 **줄었다**(27 → 42 → 12.9). 포화가 아니라 **붕괴**다.

### 서버 측 분해

액세스 로그(S15P11C204-132에서 넣은 것)에 요청마다 `pred=..ms redis=..ms`가 이미 있어
**새 계측 없이** 분해했다.

| | 스레드풀 40·fp32 | 스레드풀 4·fp32 | 스레드풀 2·fp32 | **스레드풀 2·int8** |
|---|---|---|---|---|
| 전체 p50 | 8,142ms | 4,105ms | 3,576ms | **237ms** |
| ├ 추론 | 996ms | 100ms | 53ms | **15ms** |
| ├ Redis | 104ms | 4ms | 3ms | **4ms** |
| └ 대기 | 7,173ms | 4,004ms | 3,502ms | **215ms** |
| 초당 완료 메시지 | 40 | 80 | 87 | **227** |
| 초당 완료 요청 | 15 | 25 | 27 | **50** |

## 3. 병목 — 대기열 (추론이 아니었다)

### 원인

`/ingest`는 동기 함수(`def`)라 FastAPI가 anyio 스레드풀에 넘긴다. **기본 40개인데 CPU는 2코어다.**
받아들이는 양이 처리 능력의 20배라 40개 스레드가 2코어를 두고 경합한다.

```
한산할 때  64건 317ms  건당   5.0ms
부하 중     4건 996ms  건당 249.0ms      ← 메시지 16배 적은데 3배 느림
```

Redis가 3ms → 104ms로 **35배** 느려진 것이 결정적이다. Redis는 네트워크 왕복이라 CPU를
거의 안 쓰는데도 느려졌다 — 스레드가 코어를 못 얻어 응답 처리조차 밀렸다는 뜻이다.

**동기(`def`)로 쓴 것 자체는 옳았다.** `clf.predict()`가 CPU를 붙잡고 Redis 클라이언트도
동기라, `async def`에 넣으면 이벤트 루프 전체가 얼어붙어 더 나빠진다.
문제는 **동시 허용량(40)이 실제 처리 능력(2코어)의 20배**라는 점이다.

### 검증

스레드풀을 40 → 2로 줄이자 **추론 19배(996→53ms)·Redis 35배(104→3ms) 빨라지고
처리량이 7.7배**가 됐다. 모델·CPU·코드는 그대로다. 순수한 경합 제거 효과다.

대기 **비중**이 88% → 98%로 오른 것은 나빠진 게 아니다. 대기가 서버 안(경합)에서
큐(순서 기다림)로 옮겨간 것이고 전체 시간은 절반이 됐다. 큐에서 기다리는 요청은 자원을 쓰지 않는다.

## 4. int8 — 측정 중 판단을 뒤집은 지점

### 처음에 잘못 판단했다

스레드풀 2 시점에 추론이 전체의 **1.5%**(53ms / 3,576ms)로 내려가자
"int8로 절반을 줄여도 전체의 0.7%밖에 안 되니 무의미하다"고 결론지었다. **이는 틀렸다.**

**지연 구성비와 처리 능력을 혼동한 것이다.** 대기 98%는 독립적인 비용이 아니라
**처리가 느려서 생긴 결과**다. 처리량은 요청당 실제 CPU 작업량이 정한다:

```
fp32 :  추론 53ms + Redis 3ms = 56ms  ->  2코어 / 56ms ≈ 36 req/s
int8 :  추론 27ms + Redis 3ms = 30ms  ->  2코어 / 30ms ≈ 67 req/s
```

**작업 시간을 절반으로 줄이면 처리 능력이 2배가 되고, 그러면 대기가 통째로 사라진다.**
실측에서 왕복이 8,891ms → 472ms로 **19배** 좋아졌다. 처음 계산했던 "0.7% 개선"과 전혀 다르다.

> 교훈: 포화 상태에서 지연의 구성비만 보고 개선 효과를 추정하면 안 된다.
> 큐잉 지연은 서비스 시간에 비선형으로 반응한다.

### 두 조치의 기여도

```
기본 (스레드 40, fp32)     12.9 TPS · 오류 84.6%
스레드풀 2                 98.9 TPS · 오류  0%      7.7배
+ int8                    217.6 TPS · 오류  0%      추가 2.2배
                                                    합계 17배
```

**둘 다 필요했다.** 스레드풀만으로는 99 TPS(목표의 44%)에 그친다.

### 대가

`classifier.py` 주석: *"int8은 2배 빠르지만 macro-F1이 약 1.9점 낮다. 현재 배포 기준은 fp32 —
처리량이 부족할 때만 int8로 전환."*

**"처리량이 부족할 때"가 이번에 확인된 상황이다.** 현재 8분류 macro-F1이 0.714이므로
int8 적용 시 **약 0.695**가 된다. 이 값은 골드셋 1,000건으로 재확인이 필요하다(미수행).

## 5. 권고

| 조치 | 효과 | 비용 | 판단 |
|---|---|---|---|
| **스레드풀 40 → 2** | 처리량 7.7배 | 설정 1줄 | **적용 권고** |
| **int8 전환** | 추가 2.2배 → 목표 96% 달성 | macro-F1 약 1.9점 | **적용 권고** (F1 재측정 후) |
| CPU 2 → 4코어 | 미측정 | Spring 자원 잠식 | **하지 않음** — 2코어는 Spring 몫으로 의도적으로 비워둔 것 |
| 요청 병합 | 배치 64건일 때 건당 5ms (현재 4~5건이라 건당 20ms+) | 구조 변경 | 필요 시 후속 |

### 적용 방법

스레드풀은 `server.py`의 lifespan에서 한 줄이면 된다(실험에서는 `threadpool_patch.py`로 대신했다):

```python
anyio.to_thread.current_default_thread_limiter().total_tokens = 2
```

int8은 환경변수만 바꾸면 된다:

```
CHATAI_INT8=1
```

**둘 다 추론 로직을 건드리지 않는다.**

### 남은 여유

한계가 약 260 TPS이고 목표가 227이므로 여유는 **15%**다. 1단계 실측상 동시 방송 50개의
합산 피크 max가 261이었으므로 **최악의 경우와 거의 같다.** 방송 수가 더 늘면 증설이 필요하다.

## 6. 이 측정의 한계

1. **부하 분포를 균등 배분으로 근사했다.** 실제 합산 피크 순간은 "0건 24개 + 30건 1개"처럼
   치우쳐 있는데 4~5건씩 균등하게 보냈다. **요청 수는 같아 대기열 결론은 유효**하지만,
   큰 배치가 섞일 때의 추론 시간은 낙관적으로 추정됐을 수 있다.
   → `timeline.csv`에 실측 초당 분포가 있으므로 그대로 재생하도록 개선 가능.

2. **GMS_KEY를 비우고 측정했다.** 질문으로 분류된 채팅의 Redis 적재(`lpush`·`ltrim`·`expire`)가
   빠져 실제보다 Redis 부하가 낮다. 추론 시간에는 영향 없다. 질문 적재 단가는 별도 측정 후 합산 필요.

3. **로컬 환경(2코어 컨테이너) 측정이다.** 배포 서버는 4 vCPU를 Spring·PostgreSQL·Redis와
   공유한다. chat-ai에 2코어를 준 것은 같으나 다른 프로세스의 간섭이 다르다.

4. **int8의 정확도 손실을 재측정하지 않았다.** 주석의 "1.9점"은 이전 측정값이다.
   골드셋 1,000건으로 재확인해야 한다.

5. **단계별 서버 로그를 분리하지 못했다.** 로그가 누적돼 단계들이 합산 집계됐다.
   단계별로 보려면 시간 구간 필터가 필요하다.

## 7. 산출물

```
AI/bench/
  flow_stats.py         1단계: jsonl -> 유량 지표 (sessions.csv / timeline.csv / summary.json)
  load_ingest.py        2단계: 부하 주입 (requests.csv / stages.json)
  parse_access.py       서버 액세스 로그 -> 추론·Redis·대기 분해
  threadpool_patch.py   실험용 래퍼. 서버 코드 무변경, 읽기 전용 마운트
  compose.bench.yaml    부하용 오버레이 (GMS 차단 + 스레드풀·int8 조절)
  REPORT.md             이 문서
```

**서버 코드는 한 줄도 바뀌지 않았다.** 계측은 기존 액세스 로그를 재사용했고,
스레드풀 실험은 읽기 전용 마운트로 얹었다.
`bench/`를 `.dockerignore`에 추가하면 이미지에도 들어가지 않는다.

### 재현

```bash
# 1단계
python flow_stats.py --data <데이터경로> --out out_full

# 2단계 (서버를 부하용 구성으로 기동)
BENCH_DIR=<bench 절대경로> BENCH_THREADPOOL=2 BENCH_INT8=1 \
  docker compose -f compose.yaml -f <bench>/compose.bench.yaml up -d --force-recreate chat-ai

python load_ingest.py --data <데이터경로> --env-file <AI/.env> \
  --stages 0.25,0.5,1,2 --sustain-sec 20

# 서버 측 분해
python parse_access.py <AI/logs/chatai.log> --bid-prefix bench
```
